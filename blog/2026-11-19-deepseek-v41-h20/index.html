Optimizing DeepSeek-V4.1-Flash PD & Colocate Serving on H20-3e

by: Siyuan Chen, Bingjia Wang, Bofeng Jiang, Yongxu Ai, and Kaixin Shen — Ant International AI Infra Team, Nov 19, 2026

Overview

We optimized disaggregated DeepSeek-V4.1-Flash serving on H20-3e by tuning prefill and decode parallelism, supporting BCG with prefill CP and bounded SWA replay, and speeding up Indexer kernels. Compared with TP4, the final configuration cut mean end-to-end latency by 65.5% and delivered 2.91× the output throughput.

Our intra-node PD deployment used four GPUs each for prefill and decode, with KV cache transfers over NVLink. Mean end-to-end latency fell from 13.63 s to 4.70 s, and output throughput rose from 847 to 2,465 tokens/s. Prefill context parallelism paired with decode data parallelism gave the largest gain, followed by FP8 DeepGEMM scoring.

Most of the latency gain came before the first token. Mean time to first token (TTFT) fell from 12.04 s to 1.89 s. Mean time per output token after the first (TPOT) rose from 3.20 to 5.62 ms. At fixed concurrency, faster prefill can keep decode busier, and faster decode can free client slots for new prompts. That can shift queueing between the two workers.

In the original sweep, the median prefill queue fell from 15 requests at baseline to 9 after CP and DP, then to 4 after DeepGEMM and 3 after breakable graphs. It reached zero with TP MoE. The median decode queue stayed at zero.

1. Prefill CP and Decode DP

Prefill handles many token rows from a single long request. Interleaved context parallelism assigns those rows to different ranks so the four GPUs can work on the same request. Decode has many active requests with a small number of query rows each. Data-parallel attention and a data-parallel LM head assign independent requests to different ranks.

Mean TTFT fell from 12.04 s to 5.16 s in this step. Mean TPOT rose from 3.20 to 4.79 ms.

Serving result. Mean E2E went from 13,633.80 to 7,547.46 ms (−44.64%). Output throughput rose from 846.76 to 1,537.90 tokens/s (+81.62%).

2. FP8 DeepGEMM for the Prefill Indexer

The Indexer scores visible keys before selecting a small subset for attention. On Hopper, we gather each request's packed FP4 keys once, convert queries and keys to FP8 E4M3, and call DeepGEMM's fp8_mqa_logits in each prefill Indexer layer. Each query can still see only the keys allowed by its causal mask and candidate set.

The queries are already FP4 fake-quantized, so we cast them to E4M3 without applying another scale. For keys, we apply the FP4 block's power-of-two scale in FP32 and clamp to −448 to +448 before casting. This keeps out-of-range values finite. DeepGEMM gets unit key scales because the block scales are already applied.

The power-of-two scaling preserves exactly representable values. Out-of-range keys saturate, very small values can round or underflow, and the change in scoring precision can affect rankings. In a separate prefill probe on a 64K prompt, we sampled 64 query rows across 8 Indexer layers. None of the 16,774,528 sampled key values needed clamping. The BF16 and DeepGEMM scorers shared 99.08% of the selected top-k entries on those same rows.

Serving result. Mean E2E went from 7,547.46 to 5,294.89 ms (−29.85%). Output throughput rose from 1,537.90 to 2,200.82 tokens/s (+43.11%). SGLang PR #49066

3. Breakable CUDA Graphs for Prefill

Long prefill runs launch many small kernels. Breakable CUDA Graphs capture the graph-safe stretches and replay them together, while operations that need live metadata stay eager. Bounded sliding-window attention (SWA) replay runs the late layers on the shorter decoder tail and stays enabled throughout the sweep. The pinned experiment branch supports interleaved prefill CP with breakable graphs and bounded replay by capturing the tail in separate graph buckets. This combination requires the experiment branch. Experiment branch implementation, SGLang PR #40333, SGLang PR #43089.

At step 3, with an 8,192-token capture size and a 262,144-token graph context cap, startup logs reported 14.53–14.59 GB of capture memory per prefill rank and about 388 s to capture. The context cap limits the size of capture buffers. SGLang PR #36534

Serving result. Mean E2E went from 5,294.89 to 5,100.87 ms (−3.66%). Output throughput rose from 2,200.82 to 2,290.05 tokens/s (+4.05%).

4. Tensor-Parallel MoE

Expert parallelism assigns different experts to different ranks. When routing favors a few experts, their ranks do more work and the other ranks wait at the collective. Tensor-parallel MoE shards each expert across all four ranks, so uneven routing no longer puts more expert work on one GPU than another.

In a separate decode profile, an early EP rank spent about 100 µs waiting for a late rank at an all-reduce. TP made the expert GEMMs slightly slower in that profile and left total verification time roughly unchanged. In prefill, the two profiled batches below took 771 ms with EP and 657 ms with TP despite slower expert GEMMs with TP.

We compared against EP with --moe-a2a-backend none. This setup did not support DeepEP or MegaMoE all-to-all. In future work, we plan to test EP with all-to-all and expert parallel load balancing (EPLB), aiming to keep the faster GEMMs while balancing workload across GPUs.

Serving result. Mean E2E went from 5,100.87 to 4,811.81 ms (−5.67%). Output throughput rose from 2,290.05 to 2,425.96 tokens/s (+5.93%).

5. Larger Indexer Score Tiles

The Indexer limits the size of its temporary score matrix. With 16K compressed keys, the 64 MiB budget fits about 1,000 query rows, so a larger batch repeats scoring and selection across tiles. Raising the prefill limit to 2 GiB lets more rows share a tile. The limit is per rank and the scorer uses the space while processing the tile. Prefill KV capacity stayed at 1,945,088 tokens with --mem-fraction-static 0.8.

Serving result. Mean E2E went from 4,811.81 to 4,773.97 ms (−0.79%), within the run-to-run variation. SGLang PR #49067

6. Fuse Prefill Selection and Writeback

The Indexer needs both candidate block IDs for later layers and physical KV slots for attention. Triton selects blocks from their maximum scores. It reduces and selects in one launch on smaller inputs, and reduces in parallel before selecting on wider inputs. A separate fused writeback filters invalid picks, sorts the remaining positions, and translates them to KV slots in one launch. The selector uses the same scores and can pick different block IDs at ties. Its tie-break favors lower block IDs, while Torch topk does not promise a stable tie order.

Serving result. Mean TTFT fell from 1,838.15 to 1,802.77 ms (−1.92%). Mean E2E stayed around 4.77 s across 45 runs with fusion enabled. SGLang PR #49069

7. Reuse Paged Indexer K Tiles During Verification

DSpark verifies several query rows from the same request in one forward pass. Those rows look at nearly the same keys. The paged scorer loads and dequantizes one FP4 K tile into BF16, then reuses it for the request's query rows. Each row still applies its own causal limit.

Serving result. Mean TPOT fell from 5.96 to 5.62 ms, and mean E2E fell from 4,774.47 to 4,698.65 ms (−1.59%). Output throughput rose by 0.99%. SGLang PR #49068

8. Colocate Serving Optimization

We ran the same request workload at concurrency 24 on a single four-GPU worker with DSpark. Compared with the BF16 TP4 baseline, mean E2E fell from 18.62 s to 7.96 s (57.26% lower), and output throughput rose from 642 to 1,483 tokens/s (130.79% higher).

Cumulative configuration Mean E2E (ms) Output (tok/s)
TP baseline (BF16 prefill Indexer) 18,619.53 642.46
Prefill CP, decode TP (BF16 prefill Indexer) 12,499.25 (-33%) 949.97
FP8 DeepGEMM 9,727.21 (-22%) 1,222.38
Breakable CUDA Graphs 9,418.85 (-3%) 1,256.71
Paged K-tile reuse 8,694.89 (-8%) 1,367.96
Tensor-parallel MoE 8,632.46 (-1%) 1,377.49
Batch-wise prefill CP and decode DP 7,957.13 (-8%) 1,482.72

We added batch-wise prefill CP and decode DP to the same worker. Prefill still splits prompt tokens across four ranks. During decode and target verification, each rank instead handles a slice of the batches with all attention heads, and the worker gathers the results back into batch order.

Adding decode DP to the prefill CP configuration cut mean E2E by 7.82% and raised output throughput by 7.64%. Decode DP requires replicated KV and Indexer keys. With the same --max-running-requests 64, the startup log reported 955,136 KV token slots with decode TP and 953,088 with decode DP. Those counts measure the KV pool. The supported concurrency also depends on the length of live sequences. SGLang PR #45729

For this workload, the colocated configuration produced more output tokens per second per GPU (371 vs. 308). The eight-GPU PD configuration delivered lower mean latency (4.70 vs. 7.96 s) and higher total throughput.

Reproduction

Use commit b07c70112c175eb7ca3c157c7bbc7847cc398d7d on the public SYChen123/sglang:v4.1/h20-dev-pd-blog branch. The commands use the DeepSeek-V4.1-Flash checkpoint. The H20 follow-up environment used PyTorch 2.14.1, Triton 3.8.0, sgl-deep-gemm==0.2.2, humming-kernels==0.1.12, mooncake-transfer-engine-cuda13==0.3.10.post2, and sglang-router==0.3.2. On the experiment branch, SGLANG_DSV41_TORCH_PREFILL_INDEXER=1 selects BF16 Torch scoring. To use FP8 DeepGEMM on Hopper, set it to 0 and select SGLANG_DSV41_SM90_PREFILL_INDEXER=deepgemm.

Steps 2 and 5–7 and colocated decode DP are still under upstream review. The four Indexer PR branches use the same names for their respective switches as the ablation table below. Run these commands on the pinned experiment revision, which also supports prefill CP with breakable graphs and bounded SWA replay.
