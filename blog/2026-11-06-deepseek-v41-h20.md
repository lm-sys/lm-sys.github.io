## Overview

On eight H20-3e GPUs, split evenly between prefill and decode, the final configuration lowered mean end-to-end latency from **13.63 s to 4.67 s** and increased output throughput from **847 to 2,501 tokens/s (2.95×)**. Prefill context parallelism with decode data parallelism gave the largest gain, followed by FP8 DeepGEMM scoring.

Most of the latency gain came before the first token. Mean time to first token (TTFT) fell from 12.04 s to 1.91 s, while mean time per output token after the first (TPOT) went from 3.20 to 5.52 ms. Faster prefill can send more work to decode, and faster decode can free up client slots for new prefill requests. With 24 requests in flight, both effects can move queueing between workers. Mean request latency and aggregate throughput also respond differently to the time spent filling and draining the run.

In the original sweep, scheduler snapshots from the middle 80% of each run show sustained prefill queueing early on. From TP4 through breakable graphs, the median prefill queue fell from 15 requests to 9, 4, and 3. With TP MoE, the median was zero. Decode's allocation and ready queues had a median of zero throughout.

## Measurement Setup

The router sends each request through prefill and decode. The workers transfer the KV state directly over intra-node Mooncake NVLink. The baseline runs TP4 attention and EP4 MoE on both workers with eager BF16 Torch prefill scoring. Every run uses the same DeepSeek-V4.1-Flash checkpoint, Humming MoE backend (w4a8), DSpark block size 5, 8192-token prefill chunks.

## 1. Prefill CP and Decode DP

Prefill handles many token rows from a single long request. Interleaved context parallelism assigns those rows to different ranks so the four GPUs can work on the same request. Decode has many active requests with a small number of query rows each. Data-parallel attention and a data-parallel LM head assign independent requests to different ranks.

| Worker | Baseline attention | Step 1 attention | MoE in both |
| --- | --- | --- | --- |
| Prefill | TP4 | Interleaved CP4 | EP4 |
| Decode | TP4 | DP4 attention and LM head | EP4 |

Mean TTFT fell from 12.04 s to 5.16 s in this step. Mean TPOT rose from 3.20 to 4.79 ms.

**Serving result.** Mean E2E went from **13,633.80 to 7,547.46 ms (−44.64%)**. Output throughput rose from **846.76 to 1,537.90 tokens/s (+81.62%)**.

## 2. FP8 DeepGEMM for the Prefill Indexer

The Indexer scores visible keys before selecting a small subset for attention. On Hopper, we gather each request's packed FP4 keys once, convert the queries and keys to E4M3, and call DeepGEMM's `fp8_mqa_logits` for every prefill Indexer layer. The scorer masks positions beyond each query's causal boundary, and candidate consumers keep their original candidate set.

The queries are already FP4 fake-quantized, so we cast them to E4M3 without applying another scale. For keys, we apply the FP4 block's power-of-two scale in FP32 and clamp to **−448 to +448** before casting. This keeps out-of-range values finite. DeepGEMM gets unit key scales because the block scales are already applied.

The power-of-two scaling preserves exactly representable values. Out-of-range keys saturate, very small values can round or underflow, and the change in scoring precision can affect rankings. In a separate prefill probe on a 64K prompt, we sampled 64 query rows across 8 Indexer layers. 0 of 16,774,528 sampled key values clamped to E4M3's range (0.0000%). The BF16 and DeepGEMM scorers shared 99.08% of the selected top-k entries on those same rows.

![Torch scores in BF16; DeepGEMM scores in E4M3 after scaling and clamping the FP4 keys](/images/blog/deepseek-v41-h20/fp8-indexer.svg)

**Serving result.** Mean E2E went from **7,547.46 to 5,294.89 ms (−29.85%)**. Output throughput rose from **1,537.90 to 2,200.82 tokens/s (+43.11%)**. [SGLang PR #49066](https://github.com/sgl-project/sglang/pull/49066)

## 3. Breakable CUDA Graphs for Prefill

Long prefill runs launch many small kernels. Breakable CUDA Graphs capture the graph-safe stretches and replay them together, while operations that need live metadata stay eager. Bounded sliding-window attention (SWA) replay runs the late layers on the shorter decoder tail and stays enabled throughout the sweep. The pinned experiment branch supports interleaved prefill CP with breakable graphs and bounded replay by capturing the tail in separate graph buckets. This combination requires the experiment branch. [Experiment branch implementation](https://github.com/SYChen123/sglang/commit/6b34308ca3484906e065bc3740e43eaf47a3d91e), [SGLang PR #40333](https://github.com/sgl-project/sglang/pull/40333), [SGLang PR #43089](https://github.com/sgl-project/sglang/pull/43089).

At step 3, with an 8,192-token capture size and a 262,144-token graph context cap, startup logs reported **14.53–14.59 GB** of capture memory per prefill rank and **about 388 s** to capture. The context cap limits the size of capture buffers. [SGLang PR #36534](https://github.com/sgl-project/sglang/pull/36534)

**Serving result.** Mean E2E went from **5,294.89 to 5,100.87 ms (−3.66%)**. Output throughput rose from **2,200.82 to 2,290.05 tokens/s (+4.05%)**.

## 4. Tensor-Parallel MoE

Expert parallelism assigns different experts to different ranks. When routing favors a few experts, their ranks do more work and the other ranks wait at the collective. Tensor-parallel MoE shards each expert across all four ranks, so uneven routing no longer puts more expert work on one GPU than another.

In a separate decode profile, an early EP rank spent about **100 µs** waiting for a late rank at an all-reduce. TP made the expert GEMMs slightly slower in that profile and left total verification time roughly unchanged. In prefill, the two profiled batches below took **771 ms with EP** and **657 ms with TP** despite slower expert GEMMs with TP.

We compared against EP with `--moe-a2a-backend none`. This setup did not support DeepEP or MegaMoE all-to-all. Next we plan to test EP with all-to-all and expert parallel load balancing (EPLB), aiming to keep the faster GEMMs while balancing work across GPUs.

## 5. Larger Indexer Score Tiles

The Indexer limits the size of its temporary score matrix. With 16K compressed keys, the **64 MiB** budget fits about 1,000 query rows, so a larger batch repeats scoring and selection across tiles. Raising the prefill limit to **2 GiB** lets more rows share a tile. The limit is per rank, and the eager scorer only holds the score tensor while processing the tile. The reported prefill KV capacity stayed at 1,945,088 tokens with `--mem-fraction-static 0.8`.

**Serving result.** Mean E2E went from **4,811.81 to 4,764.84 ms (−0.98%)**. Output throughput went from **2,425.96 to 2,456.87 tokens/s (+1.27%)**. The comparison also changes the decode budget from 128 to 512 MiB. [SGLang PR #49067](https://github.com/sgl-project/sglang/pull/49067)

## 6. Fuse Prefill Selection and Writeback

The Indexer needs both candidate block IDs for later layers and physical KV slots for attention. Triton selects blocks from their maximum scores. It reduces and selects in one launch on smaller inputs, and reduces in parallel before selecting on wider inputs. A separate fused writeback filters invalid picks, sorts the remaining positions, and translates them to KV slots in one launch. The selector uses the same scores and can pick different block IDs at ties. Its tie-break favors lower block IDs, while Torch `topk` does not promise a stable tie order.

![Triton reduces the work for candidate publishing and fuses KV-slot writeback into one launch](/images/blog/deepseek-v41-h20/selection-fusion.svg)

**Serving result.** Mean E2E went from **4,764.84 to 4,735.79 ms (−0.61%)**. Output throughput went from **2,456.87 to 2,441.95 tokens/s (−0.61%)**. [SGLang PR #49069](https://github.com/sgl-project/sglang/pull/49069)

## 7. Reuse Paged Indexer K Tiles During Verification

DSpark verifies several query rows from the same request in one forward pass. Those rows look at nearly the same keys. The paged scorer loads and dequantizes one FP4 K tile into BF16, then reuses it for the request's query rows. Each row still applies its own causal limit.

![Verify queries switch from one load and dequantization each to one shared BF16 key tile](/images/blog/deepseek-v41-h20/verify-reuse.svg)

**Serving result.** Mean E2E went from **4,735.79 to 4,668.62 ms (−1.42%)**. Output throughput went from **2,441.95 to 2,501.43 tokens/s (+2.44%)**. [SGLang PR #49068](https://github.com/sgl-project/sglang/pull/49068)

## 8. Colocated Prefill CP and Decode DP

We ran the same request workload at concurrency 24 on a single four-GPU worker with DSpark. Compared with the BF16 TP4 baseline, mean E2E fell from **18.62 s to 7.96 s** (57.26% lower), and output throughput rose from **642 to 1,483 tokens/s** (130.79% higher). The first three rows are from the follow-up sweep. The later rows are from the original colocated sweep.

| Cumulative configuration | Mean E2E (ms) | Output (tok/s) |
| --- | ---: | ---: |
| TP baseline (BF16 prefill Indexer) | 18,619.53 | 642.46 |
| Prefill CP, decode TP (BF16 prefill Indexer) | 12,499.25 | 949.97 |
| FP8 DeepGEMM | 9,727.21 | 1,222.38 |
| Breakable CUDA Graphs | 9,418.85 | 1,256.71 |
| Paged K-tile reuse | 8,694.89 | 1,367.96 |
| Tensor-parallel MoE | 8,632.46 | 1,377.49 |
| Batch-wise prefill CP and decode DP | 7,957.13 | 1,482.72 |

We added batch-wise prefill CP and decode DP to the same worker. Prefill still splits prompt tokens across four ranks. During decode and target verification, each rank instead handles a slice of the query rows with all attention heads, and the worker gathers the results back into batch order.

![Both colocated configurations split prefill tokens; decode switches from splitting heads to splitting query rows](/images/blog/deepseek-v41-h20/colocated-cp-dp.svg)

Adding decode DP to the prefill CP configuration cut mean E2E by **7.82%** and raised output throughput by **7.64%**. Decode DP requires replicated KV and Indexer keys. With the same `--max-running-requests 64`, the startup log reported 955,136 KV token slots with decode TP and 953,088 with decode DP. The log reports pool size. We did not measure the maximum number of live sequences that fits in each layout. [SGLang PR #45729](https://github.com/sgl-project/sglang/pull/45729)

For this workload, the colocated configuration produced more output tokens per second per GPU (**371 vs. 313**). The eight-GPU PD configuration delivered lower mean latency (**4.67 vs. 7.96 s**) and higher total throughput.

### PD ablations

For the Step 5–7 reruns, set `SGLANG_OPT_DSV41_LARGE_INDEXER_SCORE_BUDGET=1` on the decode worker to use 512 MiB throughout. The comparison between Step 4 and Step 5 therefore includes the decode setting change as well as the prefill change.
