## Overview

On eight H20-3e GPUs, split evenly between prefill and decode, the final configuration lowered mean end-to-end latency from **13.63 s to 4.71 s** and increased output throughput from **847 to 2,480 tokens/s (2.93×)**. Prefill context parallelism with decode data parallelism gave the largest gain, followed by FP8 DeepGEMM scoring.

![Compared with TP4, the final PD configuration has 0.35× mean end-to-end latency, 2.93× output throughput, and 0.17× mean time to first token.](/images/blog/deepseek-v41-h20/pd-performance.svg)

Most of the latency gain came before the first token. Mean time to first token (TTFT) fell from 12.04 s to 2.01 s, while mean time per output token after the first (TPOT) rose from 3.20 to 5.40 ms. Faster prefill can send more work to decode, and faster decode can free up client slots for new prefill requests. With 24 requests in flight, both effects can move queueing between workers. Mean request latency and aggregate throughput also respond differently to the time spent filling and draining the run.

Scheduler logs show where requests waited. From TP4 through breakable graphs, the median prefill queue fell from 15 requests to 9, 4, and 3. It was 0, 0, 0, and 1 in steps 4–7. Decode's allocation and ready queues had a median of zero throughout. These are scheduler snapshots from the middle 80% of each run. They point to sustained prefill queueing early in the sweep and much smaller queues later.

## Measurement Setup

The router sends each request through prefill and decode. The workers transfer the KV state directly over intra-node Mooncake NVLink. The baseline runs TP4 attention and EP4 MoE on both workers with eager BF16 Torch prefill scoring. Every run uses the same DeepSeek-V4.1-Flash checkpoint, Humming MoE backend (w4a8), DSpark block size 5, 8192-token prefill chunks.

| Workload | Value |
| --- | --- |
| Requests and concurrency | 256 requests, 24 in flight |
| Nominal input | 61,440 shared tokens + 4,096 request-specific tokens |
| Output | 500 tokens per request |
| Cache protocol | 10 warmup requests, then a cache flush before measurement |
| Observed cache hit rate | 93.21% |

Each row adds one change to the previous configuration. All 256 requests completed and produced 128,000 output tokens in each run. The main table shows the original sweep, with one run per configuration at concurrency 24. The roughly 1–2% changes in steps 5–7 in that table are single-run observations.

In a follow-up run, the BF16 TP4 baseline at concurrency 24 measured **13.56 s** mean E2E and **854 tokens/s**. At concurrency 8, it measured 4.80 s and 827 tokens/s. Throughput stayed near 854 tokens/s from concurrency 16 to 32, while mean E2E rose from 9.18 s to 17.84 s. In a separate concurrency-24 run with speculative metadata enabled, DSpark produced 5.368 tokens per verification step across 23,847 steps.

## 1. Prefill CP and Decode DP

Prefill handles many token rows from a single long request. Interleaved context parallelism assigns those rows to different ranks so the four GPUs can work on the same request. Decode has many active requests with a small number of query rows each. Data-parallel attention and a data-parallel LM head assign independent requests to different ranks.

| Worker | Baseline attention | Step 1 attention | MoE in both |
| --- | --- | --- | --- |
| Prefill | TP4 | Interleaved CP4 | EP4 |
| Decode | TP4 | DP4 attention and LM head | EP4 |

Mean TTFT fell from 12.04 s to 5.16 s in this step. Mean TPOT rose from 3.20 to 4.79 ms.

**Serving result.** Mean E2E went from **13,633.80 to 7,547.46 ms (−44.64%)**. Output throughput rose from **846.76 to 1,537.90 tokens/s (+81.62%)**.

## 2. FP8 DeepGEMM for the Prefill Indexer

The Indexer scores visible keys before selecting a small subset for attention. On Hopper, we gather each request's packed FP4 keys once, convert the queries and keys to E4M3, and call DeepGEMM's `fp8_mqa_logits` for every prefill Indexer layer. The scorer masks positions beyond each query's causal boundary, and candidate consumers keep their original candidate set.

The queries are already FP4 fake-quantized, so we cast them to E4M3 without applying another scale. For keys, we apply the FP4 block's power-of-two scale in FP32 and clamp to **−448 to +448** before casting. This keeps out-of-range values finite. DeepGEMM gets unit key scales because the block scales are already applied.

The power-of-two scaling preserves exactly representable values. Out-of-range keys saturate, very small values can round or underflow, and the change in scoring precision can affect rankings. We did not record the clamp rate or compare top-k overlap on the serving prompts.

![Torch scores in BF16; DeepGEMM scores in E4M3 after scaling and clamping the FP4 keys](/images/blog/deepseek-v41-h20/fp8-indexer.svg)

**Serving result.** Mean E2E went from **7,547.46 to 5,294.89 ms (−29.85%)**. Output throughput rose from **1,537.90 to 2,200.82 tokens/s (+43.11%)**. [SGLang PR #49066](https://github.com/sgl-project/sglang/pull/49066)

## 3. Breakable CUDA Graphs for Prefill

Long prefill runs launch many small kernels. Breakable CUDA Graphs capture the graph-safe stretches and replay them together, while operations that need live metadata stay eager. Bounded sliding-window attention (SWA) replay runs the late layers on the shorter decoder tail. It stays enabled throughout the sweep. The experiment branch combines interleaved prefill CP and breakable graphs by capturing the tail in separate graph buckets. [Experiment branch implementation](https://github.com/SYChen123/sglang/commit/6b34308ca3484906e065bc3740e43eaf47a3d91e), [SGLang PR #40333](https://github.com/sgl-project/sglang/pull/40333), [SGLang PR #43089](https://github.com/sgl-project/sglang/pull/43089).

At step 3, with an 8,192-token capture size and a 262,144-token graph context cap, startup logs reported **14.53–14.59 GB** of capture memory per prefill rank and **about 388 s** to capture. The context cap limits the size of capture buffers. [SGLang PR #36534](https://github.com/sgl-project/sglang/pull/36534)

**Serving result.** Mean E2E went from **5,294.89 to 5,100.87 ms (−3.66%)**. Output throughput rose from **2,200.82 to 2,290.05 tokens/s (+4.05%)**.

## 4. Tensor-Parallel MoE

Expert parallelism assigns different experts to different ranks. When routing favors a few experts, their ranks do more work and the other ranks wait at the collective. Tensor-parallel MoE shards each expert across all four ranks, so uneven routing no longer puts more expert work on one GPU than another.

In a separate decode profile, an early EP rank spent about **100 µs** waiting for a late rank at an all-reduce. TP made the expert GEMMs slightly slower in that profile and left total verification time roughly unchanged. In prefill, the two profiled batches below took **771 ms with EP** and **657 ms with TP** despite slower expert GEMMs with TP.

We compared against EP with `--moe-a2a-backend none`. This setup did not support DeepEP or MegaMoE all-to-all. Next we plan to test EP with all-to-all and expert parallel load balancing (EPLB), aiming to keep the faster GEMMs while balancing work across GPUs.

**Serving result.** Mean E2E went from **5,100.87 to 4,902.85 ms (−3.88%)**. Output throughput rose from **2,290.05 to 2,380.37 tokens/s (+3.94%)**.

## 5. Larger Indexer Score Tiles

The Indexer limits the size of its temporary score matrix. At long context lengths, a small budget fits few queries, so scoring and selection repeat across many tiles. Increasing the prefill budget from **64 MiB to 2 GiB** lets each tile cover more queries. This is a per-rank limit on one temporary score tile. The H20 scorer runs in an eager break, and the score tensor only lives for the tile. The reported prefill KV token capacity stayed at 1,945,088 with `--mem-fraction-static 0.8`.

**Serving result.** Mean E2E went from **4,902.85 to 4,827.67 ms (−1.53%)**. Output throughput rose from **2,380.37 to 2,426.16 tokens/s (+1.92%)**. [SGLang PR #49067](https://github.com/sgl-project/sglang/pull/49067)

## 6. Fuse Prefill Selection and Writeback

The Indexer needs both candidate block IDs for later layers and physical KV slots for attention. Triton selects blocks from their maximum scores. It reduces and selects in one launch on smaller inputs, and reduces in parallel before selecting on wider inputs. A separate fused writeback filters invalid picks, sorts the remaining positions, and translates them to KV slots in one launch. The selector uses the same scores and can pick different block IDs at ties. Its tie-break favors lower block IDs, while Torch `topk` does not promise a stable tie order.

![Triton reduces the work for candidate publishing and fuses KV-slot writeback into one launch](/images/blog/deepseek-v41-h20/selection-fusion.svg)

**Serving result.** Mean E2E went from **4,827.67 to 4,760.91 ms (−1.38%)**. Output throughput rose from **2,426.16 to 2,464.74 tokens/s (+1.59%)**. [SGLang PR #49069](https://github.com/sgl-project/sglang/pull/49069)

## 7. Reuse Paged Indexer K Tiles During Verification

DSpark verifies several query rows from the same request in one forward pass. Those rows look at nearly the same keys. The paged scorer loads and dequantizes one FP4 K tile into BF16, then reuses it for the request's query rows. Each row still applies its own causal limit.

![Verify queries switch from one load and dequantization each to one shared BF16 key tile](/images/blog/deepseek-v41-h20/verify-reuse.svg)

**Serving result.** Mean E2E went from **4,760.91 to 4,705.99 ms (−1.15%)**. Output throughput rose from **2,464.74 to 2,480.23 tokens/s (+0.63%)**. [SGLang PR #49068](https://github.com/sgl-project/sglang/pull/49068)

## 8. Colocated Prefill CP and Decode DP

We ran the same request workload at concurrency 24 on a single four-GPU worker with DSpark. The final configuration reached **7.96 s** mean E2E and **1,483 output tokens/s**.

| Cumulative configuration | Mean E2E (ms) | Output (tok/s) |
| --- | ---: | ---: |
| Prefill CP, decode TP, FP8 DeepGEMM | 9,682.40 | 1,229.22 |
| Breakable CUDA Graphs | 9,418.85 | 1,256.71 |
| Paged K-tile reuse | 8,694.89 | 1,367.96 |
| Tensor-parallel MoE | 8,632.46 | 1,377.49 |
| Decode DP | 7,957.13 | 1,482.72 |

We added batch-wise prefill CP and decode DP to the same worker. Prefill still splits prompt tokens across four ranks. During decode and target verification, each rank instead handles a slice of the query rows with all attention heads, and the worker gathers the results back into batch order.

![Both colocated configurations split prefill tokens; decode switches from splitting heads to splitting query rows](/images/blog/deepseek-v41-h20/colocated-cp-dp.svg)

Adding decode DP to the prefill CP configuration cut mean E2E by **7.82%** and raised output throughput by **7.64%**. Decode DP requires replicated KV and Indexer keys. With the same `--max-running-requests 64`, the startup log reported 955,136 KV token slots with decode TP and 953,088 with decode DP. The log reports pool size. We did not measure the maximum number of live sequences that fits in each layout. [SGLang PR #45729](https://github.com/sgl-project/sglang/pull/45729)

For this workload, the colocated configuration produced more output tokens per second per GPU (**371 vs. 310**). The eight-GPU PD configuration delivered lower mean latency (**4.71 vs. 7.96 s**) and higher total throughput.

## Reproduction

Use commit `49c5fae5dd224d960d34e6d444750e4b4b97f1b1` on the public [`SYChen123/sglang:v4.1/h20-dev-pd-blog` branch](https://github.com/SYChen123/sglang/tree/v4.1/h20-dev-pd-blog). The commands use the [DeepSeek-V4.1-Flash checkpoint](https://huggingface.co/deepseek-ai/DeepSeek-V4.1-Flash). The H20 follow-up environment used PyTorch 2.14.1, Triton 3.8.0, `sgl-deep-gemm==0.2.2+sm90w4a8`, `humming-kernels==0.1.12`, `mooncake-transfer-engine-cuda13==0.3.10.post2`, and `sglang-router==0.3.2`. The linked SGLang PRs track the upstream changes.

### Common worker environment

Run this block in each worker terminal. The settings hold the optional Indexer paths at their measured baseline values.

```bash
export SGLANG_ENABLE_DSV41_ENGRAM_HOST_TABLE=1 SGLANG_DSV41_ENGRAM_HOST_TABLE_LAYOUT=per_rank
export SGLANG_HUMMING_INPUT_QUANT_CONFIG='{"dtype":"float8e4m3"}'
export SGLANG_OPT_DSV41_VERIFY_INDEXER_BF16_K_REUSE=0
export SGLANG_OPT_DSV41_TRITON_PREFILL_SELECTION=0 SGLANG_OPT_DSV41_LARGE_INDEXER_SCORE_BUDGET=0
```

### Disaggregated baseline

Use two terminals on the same eight-GPU host. In each terminal, also set the PD transport environment below.

```bash
export SGLANG_HOST_IP=127.0.0.1 SGLANG_MOONCAKE_CUSTOM_MEM_POOL=INTRA_NODE_NVLINK
export MC_INTRA_NVLINK=true MC_INTRANODE_NVLINK=true
export SGLANG_DISAGGREGATION_ALL_CP_RANKS_TRANSFER=1 SGLANG_OPT_MOONCAKE_NVLINK_LAYER_BATCH=0
export SGLANG_SET_CPU_AFFINITY=1
```

Prefill uses the BF16 Torch scorer. The bounded SWA flag applies in eager mode as well as with graphs.

```bash
CUDA_VISIBLE_DEVICES=0,1,2,3 SGLANG_DSV41_TORCH_PREFILL_INDEXER=1 \
sglang serve --model-path deepseek-ai/DeepSeek-V4.1-Flash --served-model-name llm \
  --host 127.0.0.1 --port 9091 --trust-remote-code --language-model-only \
  --attention-backend dsv4 --tp 4 --ep-size 4 --moe-runner-backend humming --moe-a2a-backend none \
  --speculative-algorithm DSPARK --speculative-dspark-block-size 5 --enable-cache-report \
  --chunked-prefill-size 8192 --max-prefill-tokens 8192 --disable-prefill-cuda-graph \
  --enable-decoder-swa-bounded-replay --swa-full-tokens-ratio 0.1 --mem-fraction-static 0.8 \
  --enable-hierarchical-cache --hicache-ratio 0.25 --hicache-io-backend kernel \
  --hicache-write-policy write_through --tokenizer-worker-num 8 --detokenizer-worker-num 8 \
  --random-seed 42 --disaggregation-mode prefill \
  --disaggregation-transfer-backend mooncake --disaggregation-bootstrap-port 8998
```

Decode runs on the other four GPUs.

```bash
CUDA_VISIBLE_DEVICES=4,5,6,7 \
sglang serve --model-path deepseek-ai/DeepSeek-V4.1-Flash --served-model-name llm \
  --host 127.0.0.1 --port 9092 --trust-remote-code --attention-backend dsv4 \
  --tp 4 --ep-size 4 --moe-runner-backend humming --moe-a2a-backend none \
  --speculative-algorithm DSPARK --speculative-dspark-block-size 5 --enable-cache-report \
  --mem-fraction-static 0.85 --max-running-requests 256 \
  --tokenizer-worker-num 8 --detokenizer-worker-num 8 --random-seed 42 \
  --disaggregation-mode decode --disaggregation-transfer-backend mooncake
```

Apply these changes cumulatively and restart the workers for each measurement. Put environment assignments before `sglang serve` so they override the baseline exports.

| Step | Worker | Change from previous step |
| --- | --- | --- |
| 1. CP + DP | Prefill / Decode | Prefill adds `--enable-prefill-cp --cp-strategy interleave`. Decode adds `--dp 4 --enable-dp-attention --enable-dp-lm-head`. |
| 2. DeepGEMM | Prefill | Replace the Torch scorer assignment with `SGLANG_DSV41_TORCH_PREFILL_INDEXER=0 SGLANG_DSV41_SM90_PREFILL_INDEXER=deepgemm`. |
| 3. BCG | Prefill | Replace `--disable-prefill-cuda-graph` with `--cuda-graph-backend-prefill breakable --cuda-graph-max-bs-prefill 8192 --cuda-graph-prefill-max-context 262144`. |
| 4. TP MoE | Both | Replace `--ep-size 4` with `--ep-size 1`. |
| 5. Score tiles | Prefill | Set `SGLANG_OPT_DSV41_LARGE_PREFILL_SCORE_BUDGET=1`. |
| 6. Fusion | Prefill | Set `SGLANG_OPT_DSV41_TRITON_PREFILL_SELECTION=1`. |
| 7. K-tile reuse | Decode | Set `SGLANG_OPT_DSV41_VERIFY_INDEXER_BF16_K_REUSE=1`. |

### PD router

Start the router once both workers are healthy.

```bash
python3 -m sglang_router.launch_router --pd-disaggregation \
  --prefill http://127.0.0.1:9091 8998 --decode http://127.0.0.1:9092 \
  --host 127.0.0.1 --port 9090 --worker-startup-timeout-secs 3600 \
  --disable-circuit-breaker --prefill-policy round_robin --decode-policy round_robin
```

### Colocated baseline

Start a four-GPU worker with the common environment above. It listens on the benchmark port directly.

```bash
CUDA_VISIBLE_DEVICES=0,1,2,3 SGLANG_DSV41_TORCH_PREFILL_INDEXER=1 \
sglang serve --model-path deepseek-ai/DeepSeek-V4.1-Flash --served-model-name llm \
  --host 127.0.0.1 --port 9090 --trust-remote-code --attention-backend dsv4 \
  --tp 4 --ep-size 4 --moe-runner-backend humming --moe-a2a-backend none \
  --speculative-algorithm DSPARK --speculative-dspark-block-size 5 --enable-cache-report \
  --chunked-prefill-size 8192 --max-prefill-tokens 8192 --disable-prefill-cuda-graph \
  --enable-decoder-swa-bounded-replay --cuda-graph-max-bs-decode 64 \
  --mem-fraction-static 0.8 --max-running-requests 64 --random-seed 42 \
```
